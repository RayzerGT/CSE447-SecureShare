NOTE ON XSS: input sanitization / stored-XSS protection was considered and
dropped from scope entirely (it was only ever in the team's own project
proposal document, not in the official graded CSE447 project requirements
document - confirmed by re-reading that document directly). Comments is just
"comments" now, no sanitization sub-feature.

HIERARCHY: Developer > Admin > User - but this is NOT "higher role can do
what lower roles can" access. Each role is walled off to ONLY its own area:
    - User: the social site (feed/upload/messaging/social/comments/likes).
      No access to /moderation/ or /portal/.
    - Admin: /moderation/ ONLY - no feed/upload/messaging, no /portal/.
      Manages Standard User accounts only (lock/suspend/ban) - cannot touch
      other Admin or Developer accounts, and cannot create new admins.
    - Developer: /portal/ ONLY - no feed/upload/messaging, no /moderation/.
      Two separate menus: manage_admins (grant/revoke the Admin role) and
      manage_users (lock/suspend/ban Standard User accounts, same power
      admins have over users). Developer accounts themselves aren't managed
      through either menu.
Enforced by moderation/permissions.py::RoleAccessMiddleware (redirects
anyone whose role isn't User away from anything outside their own area)
plus queryset scoping in each management view (so even a hand-crafted
request against the right URL 404s if the target account is the wrong
role) - see Razeen's and Munia's sections below for the specific files.

New admins are created by a Developer directly registering them
(moderation/portal_views.py::manage_admins(), form=AdminCreationForm in
moderation/forms.py) - there is no promote-a-Standard-User path anymore.
Developers can also remove (demote to Standard User) or ban an admin from
the same page. Banning any account (Standard User or Admin, via
apply_account_status_action() in moderation/views.py) cascades: all of
that account's friendships are deleted (social.models.Friendship.
remove_all_for()) so their posts disappear from former friends' feeds and
they vanish from friend lists, and all of their active sessions are
revoked. Locked/suspended/banned accounts are also blocked from
logging in at all (accounts.models -> moderation.models.AccountState.
is_blocked_for(), checked in accounts/views.py::login_view()/verify_2fa()
and moderation/portal_views.py::portal_login()).

POST VISIBILITY is deliberately as simple as it gets: a post is visible to
its owner and to that owner's friends, and to nobody else. There is no
public/private/role-restricted setting, no Visibility choices field and no
posts/permissions.py - that whole feature was removed to cut complexity. The
rule lives inline in posts/views.py (feed() and detail()) using
social.models.Friendship. Note this is UNRELATED to the Admin/Developer/User
RBAC above, which is a graded requirement and stays.

FUNCTIONAL FEATURES BUILT ON TOP OF THIS SKELETON (not part of the 12
graded security requirements, but the app surface those requirements get
implemented into): Instagram-style feed, friends/following system with
search, friends-only messaging with image attachments, profile editing
(full_name/bio/avatar), and a reports/tickets pipeline (post/user/message)
that admins resolve with kind-specific actions (delete post, warn/
suspend/ban user, delete message). See each teammate's section below for
exactly which files.

FRONTEND (shared - read FRONTEND.md before writing any template)
================================================================================
The UI is Instagram-inspired for the social side and a separate dark
"console" skin for the Admin/Developer panels. Both live in ONE stylesheet
(static/css/base.css) + one shell (templates/base.html); base.html picks the
skin from the signed-in user's role automatically. The split is cosmetic -
the real wall is still moderation/permissions.py::RoleAccessMiddleware - but
it means a privileged panel never looks like the social site.

Shared files nobody should fork or duplicate:
    templates/base.html                       - page shell + role-aware skin
    templates/navbar.html                     - left rail / mobile tab bar,
                                                shows only the current role's
                                                own links
    templates/_avatar.html                    - ALWAYS render user avatars
                                                through this (handles the
                                                no-avatar letter fallback)
    templates/_page_template.html             - copy this to start a new page
    static/css/base.css, static/js/base.js
    accounts/templatetags/assets.py           - {% versioned_static %}; use it
                                                instead of {% static %} so a
                                                CSS change isn't hidden behind
                                                a stale browser cache

Per-app partials (owned by whoever owns that app's views):
    messaging/templates/messaging/_dm_list.html         -> Afnan Satter
    moderation/templates/moderation/_account_table.html -> Mos. Mahabuba Akter Munia

GOTCHA: never name a template context variable `messages` - that name belongs
to django.contrib.messages, and using it makes your data render as flash
banners. messaging/views.py::thread() uses `thread_messages` for this reason.

NOTES
================================================================================
- All from-scratch crypto requirements (RSA, ECC, password hashing, MAC) must
  NOT use built-in framework or library implementations -- see the official
  CSE447 project requirements document for the exact wording (shared
  separately by the instructor, not part of this repo).
- XSS/input-sanitization is NOT in the graded requirements document -- it
  was only in the team's own project-ideas proposal, and has been dropped
  from this plan. Don't spend time on it.
- SETTING UP A NEW MACHINE: read SQLITE_SETUP.txt. Step-by-step, ~5 minutes,
  no credentials needed. There is nothing to install for SQLite (it's built
  into Python), and requirements-sqlite.txt lets you skip mysqlclient - the
  one dependency that needs a compiler and usually breaks installs on
  macOS/Linux.
- DATABASE: the project runs on either backend, chosen by DB_ENGINE in your
  own .env (which is gitignored, so everyone's choice is independent):
      DB_ENGINE=sqlite  (default) -> local db.sqlite3 file, zero setup. Use
                                     this for day-to-day development.
      DB_ENGINE=mysql             -> the shared Aiven server. Used for the
                                     PROJECT DEMONSTRATION and shared data.
  Same code, same migrations, both ways - switching is never a code change.
      python manage.py dbinfo     -> which DB am I on? can it connect? are
                                     migrations up to date?
      python manage.py seed_demo  -> fill a fresh SQLite DB with the team's
                                     logins + sample content (idempotent;
                                     refuses to touch the shared DB without
                                     --allow-shared)
  Both commands live in accounts/management/commands/ (shared tooling, not
  account-specific - Django only discovers commands inside an installed app).
  CAUTION: a migration generated on SQLite still has to be applied to MySQL.
  Commit the migration file; whoever is on mysql runs migrate there. Before
  the demo, switch to DB_ENGINE=mysql and run dbinfo to confirm it's current.
- .env.example lists every environment variable the app reads; requirements.txt
  pins every Python dependency (see README.md "System requirements" for
  cross-platform setup instructions, and "Shared team database" for how to
  point your .env at the central MySQL database everyone uses).
- Run `python manage.py check` after any change to catch config/model errors
  early.
